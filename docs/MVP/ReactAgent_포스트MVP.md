# 음성 기반 ReAct 폰 에이전트 — 포스트 MVP

> MVP(M0–M5) 이후 **바로 구현할 항목**. 로컬 모델·스킬·라우터·외부 트리거는 여기 넣지 않는다. 그 목록은 [기획서 §7](./ReactAgent_MVP_기획.md#7-이후-확장-경로)에 그대로 둔다.
>
> **상태:** ✅ 완료 (2026-09-04, M6–M9) — speak · back · scroll · web_search 구현 및 실기기 검증 완료. M10 이후는 [기획서 §7](./ReactAgent_MVP_기획.md#7-이후-확장-경로).

---

## 완료 기준선 (M9)

음성 명령 → ReAct 루프 → 제네릭 도구 7개 + `finish` TTS까지 동작한다.

| 구분 | 상태 |
|---|---|
| 도구 | `open_app` / `tap_node` / `input_text` / `back` / `scroll` / `web_search` / `finish` |
| 음성 | 입력 (`RecognizerIntent`) + `finish` summary TTS |
| 탐색 | 탭·앱 실행·뒤로가기·목록 스크롤 |
| 지식 | `web_search`로 스니펫을 텍스트로 받음 (구글/크롬 미조작) |
| 검증 | 설정 배터리, 카톡 전송, 웹 조회(날씨 등) 실기기 통과 |

`MAX_ROUNDS = 10`. 다단계 화면·HITL(`ask_user`)·기차 예매 등은 M10 이후 확장이다.

---

## 전체 흐름

```
M6  speak → M7  back → M8  scroll → M9  web_search → M10  ask_user → M11  다단계 시나리오
   (결과 낭독)    (복구)      (목록)         (지식)          (HITL)          (검증)
```

순서 이유: 낭독은 루프를 거의 건드리지 않는다. `back`/`scroll`이 있어야 막힌 화면에서 빠져나오고 목록을 탐색한다. `web_search`는 화면과 무관한 지식 조회라 UI 도구 다음에 넣는다. 구글을 여는 경로와 검색 도구를 HITL보다 먼저 가른다. `ask_user`는 루프를 멈추므로 도구가 안정된 뒤에 넣는다. 복잡한 시나리오는 도구가 있어야 의미 있는 실패가 나온다.

각 마일스톤은 **독립적으로 실행·검증 가능한 상태**로 끝낸다.

### 버전 표기 (구현 시 필수)

마일스톤을 **구현 완료로 끝낼 때마다** 홈 화면 왼쪽 상단 마일스톤 라벨을 해당 단계로 갱신한다. 기능만 넣고 라벨을 그대로 두지 않는다.

| 항목 | 위치 | 형식 예 |
|---|---|---|
| 홈 화면 마일스톤 라벨 | `app/src/main/java/com/mystar/agent/MainActivity.kt` — `AgentHomeScreen` 제목 아래 `Text` | `M6 — finish 결과 TTS`, `M7 — back` |
| (선택) 앱 버전명 | `app/build.gradle.kts` — `versionName` | 포스트 MVP 전체를 묶어 올릴 때만 조정 |

- 라벨 문구는 **마일스톤 번호 + 한 줄 요약**으로 맞춘다.
- 각 마일스톤 **할 일**·**완료 기준(DoD)** 에 버전 갱신 체크가 있으면, 구현 PR/커밋에 포함했는지 함께 확인한다.

## M6 — `speak`: finish 결과 읽어주기

**목표:** 작업이 끝나면 사용자가 화면을 보지 않아도 결과를 듣는다.
**규모:** ~0.5일
**의존:** 없음. 기존 `finish(summary)`만 있으면 된다.
**상태:** ✅ 완료 (2026-09-04) — `TtsHelper` + `finish` 성공 경로에서 summary 한국어 TTS 낭독, 홈 라벨 `M6 — finish 결과 TTS`

### 왜

지금은 `finish`가 로그에만 남는다. 음성으로 시킨 작업의 결과는 음성으로 받아야 한다. "배터리 몇 퍼센트야", "예매 됐어?" 같은 읽기 목표에서 특히 필요하다.

### 설계

`speak`를 **LLM 도구로 새로 두지 않는다.** TTS는 앱이 `finish` 시점에 결정론적으로 수행한다.

- 엔진: Android `TextToSpeech` (한국어 `Locale.KOREA`). 별도 SDK·키 없음.
- 읽을 텍스트: `finish`의 `summary`. 비어 있으면 "작업을 마쳤습니다."
- 시점: 루프가 `finish`를 처리한 직후, 종료 이벤트를 UI에 보낸 다음.
- 실패: TTS 미초기화·언어 미지원이면 로그만 남기고 루프는 성공으로 끝낸다. 읽기 실패가 작업 실패는 아니다.

루프 중간에 말하게 할 필요는 아직 없다. 정보가 필요하면 M10 `ask_user`가 질문하고, 완료 낭독은 `finish` 한곳만 담당한다.

### 할 일

- `TextToSpeech` 초기화·해제 (Activity/`Application` 수명에 맞춤)
- `finish` 성공 경로에서 `summary`를 읽어줌
- 시스템 프롬프트: `finish`의 `summary`는 사용자에게 그대로 읽어줄 한두 문장으로 쓰라고 명시
- 홈 화면 마일스톤 라벨을 `M6 — finish 결과 TTS`로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [x] "설정 열어 배터리 알려줘"가 `finish`로 끝나면 summary가 스피커로 나온다
- [x] summary가 비어 있어도 TTS가 기본 문구를 읽고 루프는 정상 종료된다
- [x] TTS 실패 시 앱이 죽지 않고 로그에만 남는다
- [x] 홈 화면 왼쪽 상단 라벨이 `M6 — finish 결과 TTS`로 표시된다

**데모:** 음성으로 목표를 주고, 끝나면 화면을 보지 않은 채 결과 문장을 듣는다.

**함정:** TTS `onInit` 전에 speak하면 묵음. 초기화 완료 후에만 읽는다. 긴 summary는 자르지 말고 일단 그대로 읽는다.

## M7 — `back`

**목표:** 잘못된 화면에서 빠져나온다.
**규모:** ~0.5일
**의존:** 없음.
**상태:** ✅ 완료 (2026-09-04) — `AgentAccessibilityService.performBack()` + `ToolRegistry` `back` 등록, 행동 후 안정화·트리 부착, 홈 라벨 `M7 — back`

### 왜

지금은 앞으로만 간다. 잘못된 채팅·잘못된 설정 하위에 들어가면 복구가 안 된다. 기차 예매·회원가입은 뒤로가기가 일상이다.

### 설계

| 도구 | 역할 | 파라미터 |
|---|---|---|
| `back` | 시스템 뒤로가기 | `reason`만 |

- 구현: `AccessibilityService.performGlobalAction(GLOBAL_ACTION_BACK)`
- 행동 도구다. 실행 후 기존과 같이 안정화 → 최신 트리를 tool_result에 붙인다.
- node id 없음. 좌표·트리와 무관하다.

`open_app`으로 홈을 찍는 것과 바꾸지 않는다. `back`은 현재 앱 스택을 한 단계 되돌리는 것이고, `open_app`은 앱을 새로 띄운다.

### 할 일

- `AgentAccessibilityService`에 `performBack()`
- `ToolRegistry`에 `back` 등록·실행
- 시스템 프롬프트: 잘못된 화면·필요 없는 다이얼로그면 `back`. 목표 앱을 바꿀 때는 `open_app`
- 홈 화면 마일스톤 라벨을 `M7 — back`으로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [x] 설정 하위 화면에서 `back`을 호출하면 이전 화면으로 돌아간다
- [x] 행동 후 최신 트리가 tool_result에 붙는다
- [x] LLM이 카톡 시나리오에서 불필요하게 `back`만 반복하지 않는다 (스모크)
- [x] 홈 화면 왼쪽 상단 라벨이 `M7 — back`으로 표시된다

**데모:** "설정 배터리까지 들어갔다가 나와줘" — 들어가고 `back`으로 빠져나온다.

**함정:** 루트 화면에서 `back`은 앱이 내려가거나 홈으로 나간다. 프롬프트에 "목표 앱을 떠나면 안 되면 `back` 남용 금지"를 넣는다. 루프가 `back`만 반복하면 M11 전에 최대 라운드/중단으로 막는다. stuck detector는 아직 넣지 않는다.

## M8 — `scroll`

**목표:** 화면에 안 보이는 항목을 스크롤해서 찾는다.
**규모:** ~1일
**의존:** 트리에 이미 `scroll` 마크가 붙는다 (`AgentAccessibilityService`). 도구만 없다.
**상태:** ✅ 완료 (2026-09-04) — `scrollNode` + scrollable 노드 참조 맵 + 제스처 폴백, `ToolRegistry` `scroll` 등록, 홈 라벨 `M8 — scroll`

### 왜

연락처·열차 시간표·약관·설정 목록은 한 화면에 안 끝난다. 스크롤 없이 다단계 시나리오는 거의 실패한다.

### 설계

| 도구 | 역할 | 파라미터 |
|---|---|---|
| `scroll` | 스크롤 가능한 노드를 한 번 굴린다 | `node_id`, `direction` (`up`/`down`), `reason` |

- 대상: 최신 트리에서 `scroll` 마크가 있는 node id
- 구현 1순위: 해당 노드의 `ACTION_SCROLL_FORWARD` / `ACTION_SCROLL_BACKWARD`
- 액션이 실패하면(웹뷰·커스텀 리스트) 같은 노드 좌표로 짧은 스와이프 제스처 폴백
- 행동 도구. 안정화 후 최신 트리를 붙인다. 스크롤 뒤 node id는 전부 무효.

한 번에 끝까지 찾거나 텍스트를 검색하는 `scroll_to_find`는 넣지 않는다. 모델이 `scroll` → 새 트리에서 `tap_node`를 반복한다.

### 할 일

- 트리 직렬화에 node id → `AccessibilityNodeInfo` (또는 스크롤 액션용 참조) 맵. 지금은 좌표만 저장한다.
- `scroll(nodeId, direction)` + 제스처 폴백
- 시스템 프롬프트: 찾는 항목이 트리에 없으면 `scroll` 마크 노드를 굴린다. 같은 화면이 반복되면 방향을 바꾸거나 `back`
- 홈 화면 마일스톤 라벨을 `M8 — scroll`으로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [x] 설정 목록에서 화면 밖 항목이 스크롤 후 트리에 나타난다
- [x] `direction=down` / `up`이 반대로 움직이지 않는다
- [x] 스크롤 후 이전 node id로 `tap_node`하면 실패하고, 새 트리 id로는 성공한다
- [x] 홈 화면 왼쪽 상단 라벨이 `M8 — scroll`으로 표시된다

**데모:** "설정에서 (첫 화면에 없는 항목) 열어줘" — 스크롤 후 탭.

**함정:** 스크롤 가능 노드가 여러 개면(외부 리스트 + 내부 시트) 잘못된 노드를 굴릴 수 있다. 트리에 `scroll` 마크를 유지해 모델이 고르게 한다. 스크롤해도 트리가 같으면 바닥이다 — 프롬프트에 "변화 없으면 다른 행동"을 넣는다.

## M9 — `web_search`

**목표:** 조회 목표에서 구글·크롬을 조작하지 않고, 검색 결과를 텍스트로 받는다.
**규모:** ~0.5–1일
**의존:** 없음. 화면 트리·접근성 서비스와 무관하다.
**상태:** ✅ 완료 (2026-09-04) — `WebSearchClient`(Brave Search API) + `ToolRegistry` `web_search` + `ReactAgent` 트리 생략, 홈 라벨 `M9 — web_search`, 실기기 검증(날씨 조회) 통과

### 왜

지금은 날씨·시세·사실 조회도 `open_app`으로 구글/크롬을 연다. 웹 화면 트리는 빈약하고, 쿠키 배너·광고에 라운드를 쓴다. `MAX_ROUNDS = 10`에서 검색 UI만 5~8라운드가 나간다. 검색은 앱 조작이 아니라 지식 조회다. 설치된 앱 목록을 설정 앱을 열어 읽지 않는 것과 같다.

### 설계

| 도구 | 역할 | 파라미터 |
|---|---|---|
| `web_search` | 웹 검색 API로 결과를 가져온다 | `query`, `reason` |

- LLM 도구다. 실행 후 안정화하지 않고, 화면 트리를 붙이지 않는다. 검색 결과 텍스트가 observation이다.
- 제네릭 도구다. 구글 앱을 여는 도구가 아니다.
- 구현: HTTP 검색 API 1회. 한국어 스니펫이 나오는 공급자 하나를 고른다 (Tavily, Brave, Google CSE, SerpAPI 등). API 키가 필요하면 `local.properties` → `BuildConfig`. git 커밋 금지.
- 결과: 상위 3~5건. 각 건은 제목, URL, 스니펫 한 블록. 모델이 `finish(summary)`로 1~2문장 요약한다.
- 앱에 검색 엔진 선택 UI·다중 공급자 설정은 두지 않는다.

쓰지 않는 경우 (프롬프트로 구분):

| 목표 | 도구 |
|---|---|
| 날씨, 시세, 사실, 일반 웹 정보 | `web_search` |
| "구글에서 검색해서 보여줘"처럼 그 화면을 조작 | `open_app` |
| 카톡 친구, 설정 항목 등 앱 안 검색 | `tap_node` / `input_text` (`scroll`) |

### 할 일

- `ToolRegistry`에 `web_search` 등록·실행 (OkHttp, `Dispatchers.IO`)
- `ReactAgent`: 이 도구는 안정화/트리 생략. 결과 문자열만 tool_result
- 시스템 프롬프트: 조회는 `web_search`, 그 화면을 조작해야 할 때만 `open_app`. 인앱 검색은 UI 도구
- `finish` 조회 규칙: 웹 정보는 `web_search` 결과를 답한다. 배터리처럼 화면에 있는 값은 트리
- 홈 화면 마일스톤 라벨을 `M9 — web_search`로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [x] "오늘 서울 날씨 알려줘"가 구글/크롬을 열지 않고 `web_search` → `finish`로 끝난다
- [x] summary가 검색 스니펫에 있는 내용을 말하고, TTS로 읽힌다 (M6가 있으면)
- [x] API 실패 시 앱이 죽지 않고, 모델이 실패를 `finish`로 말할 수 있다
- [x] 카톡 시나리오에서 친구 찾기에 `web_search`를 쓰지 않는다 (스모크)
- [x] 홈 화면 왼쪽 상단 라벨이 `M9 — web_search`로 표시된다

**데모:** 음성으로 "오늘 서울 날씨" → 검색 1회 → 결과 낭독. 구글 앱이 뜨지 않는다.

**함정:** 모델이 카톡 친구·설정 항목에도 `web_search`를 쓸 수 있다. 프롬프트에 인앱 검색 금지를 넣는다. 검색 결과는 비신뢰 웹 텍스트다 — 트리와 같이 결과 안의 지시문은 무시. 키가 없으면 스키마에서 빼지 말고, 실행 실패로 돌려 모델이 `finish`하게 한다. 결과가 길면 상위 N건만. 페이지 본문을 가져오는 도구는 만들지 않는다.

## M10 — `ask_user` (HITL)

**상태:** ✅ 완료 (2026-09-04) — `ask_user` 도구 + 접근성 오버레이 HITL + 60s 타임아웃 + 질문 TTS, 홈 라벨 `M10 — ask_user (HITL)`

**목표:** 정보가 부족하거나 되돌릴 수 없는 행동 직전에 사람에게 묻고, 답을 받은 뒤 루프를 이어간다.
**규모:** ~1.5–2일
**의존:** M6 TTS가 있으면 질문을 읽어줄 수 있다. 필수는 아님(화면 다이얼로그만으로도 검증 가능).

### 왜

MVP 카톡은 목표에 수신자·메시지가 다 있었다. 기차 예매는 날짜·인원·좌석이 빠질 수 있고, 전송·결제·가입 완료는 확인 없이 누르면 사고가 난다. 기획서 §6·§7의 HITL이 이 도구다.

### 두 가지 용도

| 상황 | 예 | 기대 |
|---|---|---|
| 정보 부족 | 날짜·도착역·어느 딸인지 없음 | 질문 → 답 → 이어서 조작 |
| 위험 행동 | 전송, 결제, 가입 완료, 구매 | 요약 확인 → 승인/거절 |

### 설계

| 도구 | 역할 | 파라미터 |
|---|---|---|
| `ask_user` | 루프를 멈추고 사람에게 질문한다 | `question`, `kind` (`missing_info` \| `confirm`), `reason` |

`kind=confirm`일 때 답은 승인/거절. `missing_info`일 때는 자유 텍스트.

동작:

1. LLM이 `ask_user`를 고른다.
2. 루프는 도구 실행에서 **suspend**. 화면 트리를 붙이지 않는다 (사람 응답이 observation).
3. UI: 오버레이 또는 앱 다이얼로그에 `question` 표시. M6가 있으면 질문을 TTS로 읽는다.
4. 입력: 음성(`RecognizerIntent`) 또는 텍스트. `confirm`은 승인/거절 버튼 + 음성("보내", "취소").
5. 응답을 tool_result로 넣고 다음 라운드. 거절이면 모델이 `finish`하거나 다른 경로를 고른다.
6. 타임아웃(예: 60s)이면 실패 결과를 넣고 모델이 `finish`하게 한다. 무한 대기는 없다.

**위험 탭을 코드로 막지 않는다 (1차).** 시스템 프롬프트로 강제한다.

- 전송·결제·구매·가입완료·동의 등 되돌릴 수 없는 탭 **앞**에 `ask_user(kind=confirm)`
- 목표에 없는 필수 값이 화면을 진행하는 데 필요하면 추측하지 말고 `ask_user(kind=missing_info)`

프롬프트만으로는 빠질 수 있다. M11에서 전송/결제 라벨을 확인 없이 눌렀는지 보고, 그때 라벨 휴리스틱(탭 직전 가로채기)을 넣을지 결정한다. 지금은 도구 + 프롬프트만.

`ask_user`는 `finish`가 아니다. 확인 후에도 탭은 `tap_node`가 한다.

### 할 일

- `ask_user` 스키마 등록
- `ReactAgent`에서 이 도구는 안정화/트리 생략, 사람 응답을 기다림
- Activity/오버레이: 질문 표시, 음성·텍스트 입력, confirm 버튼, 타임아웃
- 시스템 프롬프트에 missing_info / confirm 규칙
- (선택) M6와 연결해 질문을 읽어줌
- 홈 화면 마일스톤 라벨을 `M10 — ask_user (HITL)`으로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [x] 수신자가 없는 카톡 목표에서 추측 전송하지 않고 누구에게 보낼지 묻는다
- [x] 답이 오면 그 텍스트로 탐색·입력을 이어간다
- [x] 전송 직전 confirm을 묻고, 거절이면 전송하지 않는다
- [x] 승인하면 전송 후 `finish`한다
- [x] 타임아웃 시 루프가 멈추지 않고 종료 쪽으로 접힌다
- [x] 홈 화면 왼쪽 상단 라벨이 `M10 — ask_user (HITL)`으로 표시된다

**데모 1:** "카톡 보내줘" → "누구에게요?" → "딸" → 이후 기존 흐름.
**데모 2:** 전송 버튼 직전 "딸에게 '사랑한다'를 보낼까요?" → 승인 후에만 탭.

**함정:** 매 탭마다 물으면 못 쓴다. confirm은 되돌릴 수 없는 행동만. 오버레이가 접근성 트리를 가리면 재개 후 트리에 다이얼로그가 섞인다 — 응답 후 오버레이를 닫고 안정화한 다음, 필요하면 그때 트리를 붙인다. 질문은 사용자에게 읽히므로 트리 원문을 그대로 넣지 않는다.

## M11 — 복잡한 로직 테스트

**상태:** 미구현 — M10 `ask_user` 이후.

**목표:** 기차 예매·회원가입처럼 화면이 많은 목표에서, 새 도구가 실제로 버티는지 확인한다.
**규모:** ~2–3일 (구현보다 실기기 디버깅)
**의존:** M6–M10. 스크롤·뒤로가기·검색·HITL 없이 돌리면 "도구 부족"과 "루프 버그"가 구분되지 않는다.

### 왜

카톡 전송은 앱 하나, 경로가 짧다. 다단계는 타이밍·스크롤·폼·확인 화면이 겹친다. 여기서 깨지는 것이 다음 루프 개선 우선순위다.

### 시나리오

앱을 하드코딩하지 않는다. 목표는 자연어, 도구는 제네릭 그대로.

#### S1. 기차 예매 (코레일/SRT 등 설치된 앱)

예: "내일 서울에서 부산 가는 기차 가장 이른 걸로 예매 직전까지 진행해줘. 결제는 하지 마."

| 단계 | 쓰는 도구 |
|---|---|
| 앱 실행 | `open_app` |
| 출발/도착·날짜 | `tap_node` / `input_text` / `scroll` |
| 빠진 정보 (날짜 모호, 좌석) | `ask_user` (missing_info) |
| 잘못된 화면 | `back` |
| 결제/예매 확정 직전 | `ask_user` (confirm) — **실제 결제는 하지 않음** |
| 결과 낭독 | `finish` + TTS |

성공 정의: 결제 직전 확인 화면까지 도달하거나, 사용자 거절로 안전하게 `finish`. 실결제 성공은 DoD가 아니다.

#### S2. 회원가입

예: "테스트용으로 (앱) 회원가입 화면까지 열어줘. 제출은 확인 받기 전에는 하지 마."

| 단계 | 쓰는 도구 |
|---|---|
| 약관·긴 폼 | `scroll` |
| 필드 입력 | `input_text` |
| 필수값 없음 (이메일·전화) | `ask_user` |
| 제출/동의 | `ask_user` (confirm) |
| 결과 | `finish` + TTS |

성공 정의: 폼을 채우고 제출 직전 HITL. 실제 계정 생성은 선택, 기본은 제출 전 중단.

#### S3. 웹 조회

예: "오늘 서울 날씨 알려줘."

| 단계 | 쓰는 도구 |
|---|---|
| 검색 | `web_search` |
| 결과 낭독 | `finish` + TTS |

성공 정의: 구글/크롬을 열지 않고 검색 1회 후 낭독. 화면 조작 도구를 쓰지 않는다.

#### S4. 회귀

기존 카톡·설정 배터리가 M6–M10 이후에도 통과하는지. `ask_user`가 카톡 전송마다 불필요하게 끼어들면 프롬프트를 조정한다. 정보가 완전한 목표의 전송 confirm은 유지하는 편이 안전하다. 카톡 친구 찾기·설정 항목에 `web_search`가 끼어들면 프롬프트를 조정한다.

### 할 일

- 위 시나리오를 실기기에서 반복, 로그·LangSmith 트레이스로 실패 지점 기록
- `MAX_ROUNDS` 재검토 (10이 부족하면 올리되, 무한 스크롤 방지는 유지)
- 실패를 분류: 타이밍 / 트리 부실 / 도구 부족 / 모델 오판 / HITL 누락 / 검색 오용
- 이 문서 하단 "테스트 기록"에 날짜·결과·후속 한 줄
- 홈 화면 마일스톤 라벨을 `M11 — 다단계 시나리오`로 갱신 (`MainActivity.kt`)

### 완료 기준 (DoD)

- [ ] S1이 결제 직전 confirm 또는 안전 `finish`까지 적어도 1회 성공
- [ ] S2가 제출 직전 confirm까지 적어도 1회 성공
- [ ] S3이 구글/크롬 없이 `web_search` → `finish`까지 적어도 1회 성공
- [ ] S4 카톡 전송·배터리 읽기가 여전히 통과
- [ ] 실패는 "다음에 고칠 한 가지"로 남긴다 (여기서 스킬 시스템을 만들지 않음)
- [ ] 홈 화면 왼쪽 상단 라벨이 `M11 — 다단계 시나리오`로 표시된다

**데모:** 음성으로 예매 목표 → 스크롤·질문·뒤로가기 → 결제 직전 "이대로 예매할까요?" → 거절 → 결과 낭독.

**함정:** 예매 앱은 웹뷰·캡차가 많다. 트리 빈약은 MVP 때부터 알려진 한계다. 캡차·본인인증은 사람 손에 넘기고 `ask_user`로 "인증 끝나면 계속"이 맞다. 테스트 중 실결제·실가입이 일어나지 않게 confirm을 먼저 확인한다.

## 도구 세트 (M9 완료 시점)

| 도구 | 역할 | 파라미터 | 트리 부착 |
|---|---|---|---|
| `open_app` | 앱 실행 | `package`, `reason` | 예 |
| `tap_node` | 탭 | `node_id`, `reason` | 예 |
| `input_text` | 입력 | `text`, `node_id`, `reason` | 예 |
| `back` | 시스템 뒤로가기 | `reason` | 예 |
| `scroll` | 목록 스크롤 | `node_id`, `direction`, `reason` | 예 |
| `web_search` | 웹 검색 | `query`, `reason` | 아니오 (검색 결과가 결과) |
| `ask_user` | HITL 질문/확인 | `question`, `kind`, `reason` | 아니오 (사람 답이 결과) |
| `finish` | 종료 + summary TTS | `summary`, `reason` | 아니오 |

M10에서 추가: `ask_user` (트리 부착 아니오, 사람 응답이 결과).

화면 관찰은 여전히 도구가 아니다. 행동 후 자동 tool_result.

## 포스트 MVP "완료" 정의

**상태:** ✅ 달성 (2026-09-04, M9)

다음이 모두 참이면 포스트 MVP(M6–M9) 완료로 본다.

1. `finish` 결과가 TTS로 낭독된다 (M6).
2. 잘못된 화면에서 `back`으로 복구하고, 목록에서 `scroll`로 항목을 찾을 수 있다 (M7·M8).
3. 날씨·사실 등 조회 목표가 구글/크롬을 열지 않고 `web_search` → `finish`로 끝난다 (M9).
4. 기존 카톡 전송·설정 배터리 시나리오가 M6–M9 이후에도 통과한다.

M10 `ask_user` · M11 다단계 시나리오는 이 범위 밖이다. 설계는 이 문서와 [기획서 §7](./ReactAgent_MVP_기획.md#7-이후-확장-경로)에 남긴다.
