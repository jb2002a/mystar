# 평가체계 (확정안)

ReAct 에이전트 런(JSON)을 두 질문으로 평가한다.

- **태스크를 잘 수행했나** → 결과
- **비효율적으로 수행하지는 않았나** → 효율(+ 시간·비용 부가 지표)

과정(필수 상태 통과율)은 두지 않는다. 경로를 강제하지 않는 한 성공한 런에서는 결과와 같은 정보이고, 필수 상태를 정의·매칭하는 비용이 크다. 실패한 런은 사람이 직접 로그를 본다(아래 "실패한 런" 참고).

## 부품 현황


| 부품      | 역할            | 현황                                         |
| ------- | ------------- | ------------------------------------------ |
| 골든셋     | 무엇을 시킬지       | `set_D0.md`                                |
| 실행기     | 같은 조건으로 반복 실행 | `EvalQueueRunner` + `run_config`           |
| 기록      | 스텝별 로그        | 런별 JSON (`tools[]`, `final_screen`, 토큰/비용) |
| **판정기** | 아래 지표 계산      | `eval-result-to-md` (`build_md.py`) — 성공 LLM judge, RRR·초과 스텝 |
| 집계/리포트  | 숫자 요약·비교      | 같은 스크립트 (성공/RRR/초과 스텝 컬럼)              |


## 지표 요약


| 축   | 지표                    | 참고         | 판정 근거                                             | 적용 범위         |
| --- | --------------------- | ---------- | ------------------------------------------------- | ------------- |
| 결과  | 성공 (0/1)              | SPA-Bench  | `final_screen`, `final_package`, `finish_summary` | 전체            |
| 효율  | RRR = 사람 스텝 / 에이전트 스텝 | AndroidLab | `tools[]` 길이 (`finish` 포함, 성공 런에서는 `rounds`와 같음) | 성공한 런         |
| 효율  | 초과 스텝 = 에이전트 − 사람     |            | 위와 동일                                              | 성공한 런         |
| 부가  | 시간·토큰·비용              |            | `elapsed_s`, `tokens_total`, `cost_usd`           | 전체 / 성공한 런 따로 |


## 1. 결과: 목표를 달성했나

런이 끝난 시점의 **최종 상태**를 보고 LLM judge가 판정한다.

**입력**

- `task`: 태스크 원문
- **성공 기준**: 태스크별로 실행 **전에** 작성한다(아래 참고)
- `final_screen`, `final_package`: 행동형·이동형의 근거
- `finish_summary`: 정보형의 근거(답이 화면이 아니라 최종 답변에 있다)

**출력**

- `verdict`: `pass` | `fail`
- `evidence`: 판정 근거 한 줄

**프롬프트 원칙**

- `finish_summary`의 주장("보냈습니다")을 그대로 믿지 말고, 행동형·이동형은 화면으로 확인할 것
- 성공 기준에 적힌 내용만으로 판정할 것. 기준 밖의 관대한 해석은 하지 않는다

## 2. 효율: 헛돌지 않았나 (RRR)

**RRR = 사람 최단 스텝 수 / 에이전트 스텝 수**. 1에 가까울수록 효율적이다.

### 스텝 정의

- **사람 스텝**: 성공 기준을 만족하는 **최단 도구 시퀀스** 길이(`finish` 포함). 태스크마다 `set_D0.md`에 한 번 고정한다. 사람의 터치 수가 아니라 에이전트 도구 단위로 센다
- **에이전트 스텝**: `tools[]` 길이. 실패한 tool 호출도 센다. 성공한 런에서는 JSON `rounds`와 같다
- 양쪽 모두 **`finish`를 센다**. 성공한 런은 항상 한 번 쓰므로 빼면 구현만 복잡해지고, 실제 LLM 라운드이기도 하다
- **`ask_user`**: 에이전트 스텝에는 모두 포함한다(confirm이든 재시도든 실제 소비한 라운드). 사람 스텝에는 성공 기준이 요구하는 **confirm 1회만** 포함한다. confirm 없이 같은 질문을 여러 번 되묻는 것은 redundancy로 남는다

### 집계·해석

- **성공한 런에만** 계산한다. 실패한 런까지 넣으면 빨리 포기할수록 효율이 좋아 보인다
- 1을 넘으면(사람 기준보다 짧게 끝남) 자르지 않고 기록한다. 사람 기준이 최단이 아니라는 신호이므로 기준을 다시 센다
- **성공률과 함께 본다**. 성공한 런만 세므로, 어려운 태스크에서 실패하고 쉬운 태스크만 성공하면 RRR이 좋아 보인다. 두 조건을 비교할 때는 **양쪽 모두 성공한 태스크끼리** RRR을 비교한다
- **초과 스텝** = 에이전트 스텝 − 사람 스텝. 사람 스텝이 작은 태스크(3, 5는 finish 포함 2)는 RRR 비율만으로는 1스텝 차이가 크게 보이므로, 리포트에 **초과 스텝을 RRR과 함께** 적는다

## 부가 지표: 시간·비용

스텝 수가 같아도 라운드가 느리거나 토큰을 많이 쓰면 RRR에 드러나지 않는다.
JSON에 이미 있는 값을 RRR 옆에 함께 적는다.

- `elapsed_s`, `tokens_total`, `cost_usd`
- 성공한 런과 전체 런을 나눠서 집계한다

## 실패한 런

지표로 만들지 않고 사람이 md 리포트(판정 카드·flow)를 본다.

- 런마다 막힌 지점·원인을 한 줄로 round 문서에 기록한다. 예: "검색 결과에서 eun을 못 고름"
- 라운드 간에 같은 실패가 줄었는지 비교하는 근거가 된다
- 실패 런이 많아져 직접 보기 어려워지면, 쌓인 메모로 실패 유형을 정하고 자동 태깅을 검토한다

## 태스크별 사전 작성 항목

결과를 보기 전에 태스크마다 `set_D0.md`에 고정한다(`tasks` 블록 밖에 적는다).

1. **성공 기준**: 한 줄
  - 행동형(1, 7, 9, 10): 목표 상태가 최종 화면에 있는가
  - 정보형(2, 3, 4, 5): 답변이 질문 조건을 만족하는가. 예: 4번은 "지금 영업 중"이라는 근거가 있어야 한다
  - 이동형(6, 8): 최종 화면이 목표 화면인가
2. **사람 최단 스텝 수**: 위 스텝 정의(`finish` 포함, 성공 기준이 요구하는 confirm 1회 포함)

## 알려진 한계


| 한계                          | 예                                                | 대응                                     |
| --------------------------- | ------------------------------------------------ | -------------------------------------- |
| 이전 런의 흔적과 이번 런의 결과를 구분하지 못함 | t01 `final_screen`에 같은 말풍선이 5개 있음(이전 시도의 잔여로 추정) | 사전조건으로 막는다(아래)                         |
| 정보형 답변의 사실 여부를 확인하지 못함      | 날씨·약국은 실시간 정보라서 `finish_summary`만으로는 맞는지 알 수 없다  | 미정. 필요하면 근거 도구의 `result`를 judge 입력에 추가 |
| 중간에 벌어진 부작용이 보이지 않음         | 엉뚱한 사람에게 보낸 뒤 eun에게 다시 보내면 결과가 통과                | 미정. 필요하면 태스크별 금지 사건 체크 추가              |
| 종료 후 화면이 전환되는 태스크           | 전화 걸기                                            | `final_package`로 확인                    |


## 사전조건으로 막을 것

이전 런의 흔적 문제는 judge보다 **실행 환경**에서 막는 편이 확실하다.
예: 전송형 태스크는 채팅방을 비우거나, 런마다 다른 문구를 사용한다.

## Judge 검증 (최초 1회)

1. 기존 JSON 20~30개(초기AB테스트, attempt1 등)를 사람이 직접 판정한다
2. 같은 JSON에 judge를 돌려 일치율을 본다. 목표는 약 90%
3. 불일치 케이스를 보고 성공 기준 문구나 judge 프롬프트를 고친다

**1회차 (2026-09-20):** attempt1 baseline 30런. 보류(태스크 2)를 빼면 사람 리포트와 9/9 일치. 기록은 `llm-judge-신뢰성.md`.

## 리포트 항목

- 태스크별 성공률, RRR, 초과 스텝, 시간·토큰·비용
- 태스크별 pass@k, pass^k (같은 태스크를 k번 실행)
  - pass@k: k번 중 1번 이상 성공. "할 수는 있나"
  - pass^k: k번 모두 성공. "믿고 맡길 수 있나"

## 운영 원칙

- 한 라운드에서는 변수를 하나만 바꾼다(`run_config.system_prompt_sha`로 추적)
