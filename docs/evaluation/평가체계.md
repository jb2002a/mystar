# 평가체계 (확정안, 미구현)

ReAct 에이전트 런(JSON)을 **LLM judge 하나로** 판정한다.
태스크 유형(행동형/정보형/이동형)과 관계없이 판정기는 하나다.
다만 근거는 `final_screen`만 쓰지 않고 **화면 + 궤적 + 최종 답변**을 함께 준다.

## 부품 현황

| 부품 | 역할 | 현황 |
|---|---|---|
| 골든셋 | 무엇을 시킬지 | `set_D0.md` |
| 실행기 | 같은 조건으로 반복 실행 | `EvalQueueRunner` + `run_config` |
| 기록 | 스텝별 로그 | 런별 JSON (`tools[]`, `final_screen`, 토큰/비용) |
| **판정기** | pass/fail 결정 | **미구현** — 이 문서의 대상 |
| 집계/리포트 | 숫자 요약·비교 | `eval-result-to-md` 스킬 (판정 결과 컬럼 없음) |

## 측정 축

1. **결과**: 태스크를 해냈나. 판정기의 주 출력이다
2. **과정**: 헛도는 행동, 루프, 필요한 `ask_user` 누락, **위험 행동**(엉뚱한 대상에게 전송 등)
3. **효율**: 라운드 수, 시간, 토큰, 비용. JSON에 이미 있다
4. **안정성**: 같은 태스크를 k번 실행해서 본다
   - pass@k: k번 중 1번 이상 성공. "할 수는 있나"
   - pass^k: k번 모두 성공. "믿고 맡길 수 있나"

## 왜 final_screen만으로 판정하지 않나

| 문제 | 예 | 보완 입력 |
|---|---|---|
| 이전 런의 흔적과 이번 런의 결과를 구분하지 못함 | t01 `final_screen`에 같은 말풍선 "오늘 병원 다녀왔어"가 5개 있음(이전 시도의 잔여로 추정). 이번 런이 실패해도 성공처럼 보인다 | `tools[]` (이번 런에 실제로 입력하고 전송했는지) |
| 정보형은 답이 화면에 없음 | t04 a1은 `web_search`만 하고 종료해서 화면이 홈이다 | `finish_summary` |
| 중간에 벌어진 일은 보이지 않음 | 엉뚱한 사람에게 보낸 뒤 뒤로 나오면 마지막 화면은 멀쩡하다 | `tools[]` |
| 종료 후 화면이 전환되는 태스크 | 전화 걸기 | `tools[]` + `final_package` |

## Judge 입출력

**입력**

- `task`: 태스크 원문
- **성공 기준**: 태스크별로 실행 **전에** 작성한다(아래 참고)
- `tools[]` 요약: 라운드마다 도구 이름 + `args`(+ 필요하면 `result`)
- `final_screen`, `final_package`
- `finish_summary`

**출력**

- `verdict`: `pass` | `fail`
- `failure_type` (fail일 때): `화면인식` / `도구선택` / `대기부족` / `루프` / `환각` / `위험행동` / `기타`
- `evidence`: 판정 근거 한 줄

**프롬프트 원칙**

- `finish_summary`의 주장("보냈습니다")을 그대로 믿지 말고, 화면과 궤적으로 확인할 것
- 성공 기준에 적힌 내용만으로 판정할 것. 기준 밖의 관대한 해석은 하지 않는다

## 성공 기준 작성 규칙

- 결과를 보기 전에 태스크마다 한 줄로 `set_D0.md`에 고정한다
- 유형별 초점
  - 행동형(1, 7, 9, 10): 이번 런에 목표 상태를 만들었는가
  - 정보형(2, 3, 4, 5): 답변이 질문 조건을 만족하는가. 예: 4번은 "지금 영업 중"이라는 근거가 있어야 한다
  - 이동형(6, 8): 최종 화면이 목표 화면인가

## 사전조건으로 막을 것

이전 런의 흔적 문제는 judge보다 **실행 환경**에서 막는 편이 확실하다.
예: 전송형 태스크는 채팅방을 비우거나, 런마다 다른 문구를 사용한다.

## Judge 검증 (최초 1회)

1. 기존 JSON 20~30개(초기AB테스트, attempt1 등)를 사람이 직접 판정한다
2. 같은 JSON에 judge를 돌려 일치율을 본다. 목표는 약 90%
3. 불일치 케이스를 보고 성공 기준 문구나 judge 프롬프트를 고친다

## 리포트 추가 항목

- 태스크별 pass@k, pass^k
- 실패 유형별 카운트
- 위험행동 건수(성공률과 별도로 표기)

## 운영 원칙

- 한 라운드에서는 변수를 하나만 바꾼다(`run_config.system_prompt_sha`로 추적)
- 실패는 `failure_type`별로 세고, 다음 개입은 가장 많은 유형부터 정한다
