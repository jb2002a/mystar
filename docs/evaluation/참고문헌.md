# 평가체계 참고문헌

`평가체계.md` 설계에 참고할 프레임워크와 논문 목록이다.
웹 검색 없이 기억에 의존해 정리했으므로 세부 수치와 연도는 원문에서 확인한다.

## 추천 읽기 순서

1. **SPA-Bench**: 우리 설계(LLM judge + 궤적 입력)와 가장 가깝다
2. **AndroidWorld**: 사전조건과 태스크 매개변수화
3. **τ-bench**: pass^k 부분
4. **AgentRewardBench**: judge 검증 방법

## 1. 모바일·GUI 에이전트 벤치마크

### AndroidWorld (Google, 2024)

- 에뮬레이터에서 실제 앱 20개, 태스크 116개를 돌린다
- 판정은 LLM이 아니라 **시스템 상태를 직접 조회**한다(예: 알람 앱 DB를 읽어 알람이 생겼는지 확인)
- 태스크를 매개변수화해서 이름·문구·시간을 매번 바꾼다. 그래서 이전 런의 흔적 문제가 생기지 않는다
- **우리에게:** "사전조건으로 막는다"를 체계화한 형태

### AndroidLab (칭화대, 2024)

- 성공률 외에 과정 지표를 따로 정의했다
  - Sub-Goal Success Rate: 중간 목표를 몇 개 달성했나
  - Reversed Redundancy Ratio: 사람 대비 얼마나 헛돌았나
  - Reasonable Operation Ratio: 의미 있는 행동의 비율
- 입력 모드를 XML(접근성 트리)과 스크린샷으로 나눠 비교한다
- **우리에게:** "과정" 축을 수치화할 때 참고

### SPA-Bench (2024)

- 판정이 2단계다
  - coarse: 화면에 핵심 요소가 있는지 문자열로 거름
  - fine: 멀티모달 LLM이 궤적 전체를 보고 판정
- 종료 사유를 분류한다(스스로 종료 / 조기 종료 / 스텝 초과)
- **우리에게:** 설계가 가장 비슷하다. 한 편만 읽는다면 이것

### LlamaTouch (2024)

- 태스크마다 반드시 거쳐야 하는 "필수 상태(essential states)"를 주석으로 달아 두고, 궤적이 그 상태들을 지났는지 확인한다
- **우리에게:** "final_screen만으로는 부족하다"를 궤적 기준으로 푼 사례

### AITW: Android in the Wild (Google, 2023)

- 대규모 사람 시연 데이터셋
- 평가가 오프라인이라 사람과 **같은 행동을 했는지**를 스텝별로 비교한다
- **우리에게:** 반면교사. 다른 경로로 성공해도 실패로 친다. 요즘은 실기기·에뮬레이터에서 직접 돌리는 온라인 평가가 주류다

### MobileSafetyBench (AAAI 2026)

- Android 에뮬레이터 기반의 모바일 기기 조작 에이전트 **안전성** 벤치마크
- 메시징·뱅킹 앱 등에서 오용, 부작용, 간접 프롬프트 인젝션에 대한 대응을 평가한다
- 최신 LLM 기반 에이전트도 작업 중 위해를 잘 막지 못했다. 안전을 우선하도록 하는 프롬프트 기법을 제안했지만 개선 여지가 크다
- **우리에게:** "위험행동" 축의 근거. 카톡·문자 전송 태스크가 바로 이 영역이다

## 2. 웹·데스크톱 에이전트 벤치마크

### WebArena (CMU, 2023)

- 태스크 유형별로 판정기를 나눈다
  - 정보형: `exact_match` / `must_include` / `fuzzy_match`(LLM)
  - 행동형: 사이트 DB·페이지 상태를 확인하는 프로그램
- **우리에게:** 행동형·정보형 구분의 출처

### OSWorld (2024)

- 데스크톱 태스크마다 **초기 상태 설정 스크립트와 평가 스크립트**를 짝으로 둔다
- **우리에게:** `run_config.precondition`을 엄밀하게 만든 형태

### τ-bench (Sierra, 2024)

- **pass^k를 제안**했다. k번 모두 성공해야 통과로 보고, 신뢰성을 잰다
- 판정은 대화가 끝난 뒤의 DB 상태를 정답 상태와 비교한다
- **우리에게:** pass^k 지표의 근거

## 3. LLM judge 연구

### Judging LLM-as-a-Judge / MT-Bench (Zheng et al., 2023)

- LLM judge의 편향을 정리했다: 위치 편향, 긴 답 선호, 자기 모델 선호
- 강한 모델 judge는 사람과 약 80% 수준으로 일치한다
- **우리에게:** judge 사용 전 기본서

### Autonomous Evaluation and Refinement of Digital Agents (Pan et al., 2024)

- 웹·안드로이드 에이전트의 궤적을 VLM이 판정하게 하고, 정답 판정기와 얼마나 일치하는지 측정했다
- **우리에게:** "judge 검증" 절차의 선행 사례

### AgentRewardBench (2025)

- 웹 에이전트 궤적에 대해 여러 LLM judge를 전문가 판정과 비교했다
- 모든 벤치마크에서 좋은 judge는 없었고, 규칙 기반 판정은 성공을 과소평가하는 경향이 있었다
- **우리에게:** "judge는 반드시 사람 판정으로 검증한다"의 근거

### An Illusion of Progress? Assessing the Current State of Web Agents (Online-Mind2Web, 2025)

- 실제 웹사이트 136개, 태스크 300개로 구성된 **온라인** 평가 벤치마크. 기존에 보고된 웹 에이전트 성능이 과대평가돼 있었다고 결론짓는다
- LLM judge **WebJudge**를 제안했다. 사람 판정과 약 85% 일치하고, 다른 벤치마크에도 잘 일반화된다
- **우리에게:** 통제되지 않은 실제 앱·사이트에서 LLM judge로 판정한다는 점이 우리와 같다. judge 프롬프트 설계의 직접 참고

## 4. 벤치마크 설계 원칙

### Establishing Best Practices for Building Rigorous Agentic Benchmarks (Zhu et al., 2025)

- 유명 에이전트 벤치마크들을 점검해 보니 **설계 결함 때문에 성능이 크게 과대·과소평가**되고 있었다는 논문. 점검표 **ABC(Agentic Benchmark Checklist)**를 제안한다
- 두 가지 타당성
  - **태스크 타당성(task validity)**: 목표 능력이 있어야만 풀 수 있는가. 지름길이나 우회로는 없는가
  - **결과 타당성(outcome validity)**: 판정 결과가 실제 성공 여부를 반영하는가
- 지적한 사례
  - τ-bench: 아무것도 하지 않는(빈 응답) 에이전트가 일부 태스크를 "성공"으로 통과
  - WebArena: 문자열 포함 판정의 허점으로 오답이 정답 처리됨
  - SWE-bench류: 테스트가 불충분해서 틀린 패치가 통과
  - 환경이 시간에 따라 바뀌면서 풀 수 없게 된 태스크
- ABC의 세 부분: 태스크 타당성 점검 / 결과 타당성 점검 / 보고(알려진 한계, 신뢰구간 등을 함께 공개)
- **우리에게**
  - **무행동 베이스라인**: 바로 `finish`하는 에이전트를 judge에 넣어 fail이 나오는지 확인한다. judge가 `finish_summary`의 주장에 속는지 점검하는 가장 싼 방법이다
  - **태스크 타당성**: 4번 "지금 여는 약국"은 무엇이 정답인지 모호하다. 성공 기준을 적을 때 판정 가능한 형태로 바꾼다
  - **환경 변화**: 실제 앱은 업데이트되고, 날씨·약국 정보는 실시간이다. 태스크가 여전히 풀 수 있는지 주기적으로 확인한다
  - **보고**: 리포트에 알려진 한계(사전조건 누락, judge 일치율 등)를 함께 적는다

## 5. 평가 통계

### Adding Error Bars to Evals (Evan Miller, Anthropic, 2024)

- 부제: "A Statistical Approach to Language Model Evaluations". 평가 점수를 점 하나가 아니라 **표본에서 나온 추정치**로 보고, 오차 막대(신뢰구간)를 함께 보고하자는 논문
- 권고 5가지
  1. **표준오차 보고**: 중심극한정리로 평균의 표준오차(SE)를 구하고, 95% 신뢰구간(±1.96·SE)을 함께 쓴다
  2. **군집 표준오차**: 문항들이 독립이 아니고 묶여 있으면(같은 지문에서 나온 여러 질문 등) 군집 단위로 SE를 구한다. 무시하면 SE가 과소추정된다
  3. **문항 내 분산 줄이기**: 같은 문항을 여러 번 샘플링해 평균낸다
  4. **쌍체 비교**: 두 모델을 같은 문항으로 비교할 때는 점수 차이를 문항별로 계산한다. 두 모델의 점수가 상관돼 있어서 분산이 줄어든다
  5. **검정력 분석**: 원하는 차이를 잡아내려면 문항이 몇 개 필요한지 실험 전에 계산한다
- **우리에게:** 표본이 작아서(태스크 10개 × 시도 k번) 가장 직접적으로 영향받는다
  - 예: 성공 7/10이면 SE ≈ √(0.7·0.3/10) ≈ 0.145, 95% 신뢰구간은 약 ±0.28이다. 7/10과 5/10은 통계적으로 구분되지 않는다
  - 같은 태스크의 여러 시도는 독립이 아니다 → 태스크 단위 군집 SE로 계산한다
  - 라운드 간 A/B(프롬프트나 모델 변경)는 같은 태스크끼리 짝지어 쌍체 비교한다
  - 개입 효과를 주장하려면 태스크당 몇 번을 돌려야 하는지 검정력 분석으로 미리 정한다

## 6. 원조와 도구

- **ReAct** (Yao et al., 2022): 평가는 단순했다. HotpotQA는 정답 일치(EM), ALFWorld·WebShop은 성공률·점수. 궤적 평가라는 개념은 이후 연구에서 발전했다
- **AgentBench** (2023): 여러 환경을 묶은 종합 벤치마크. 실패 원인 분류(형식 오류, 루프, 스텝 초과 등)를 참고할 만하다
- **LangSmith**: 이 프로젝트에 이미 연동돼 있다(`tracing/LangSmithClient.kt`). Dataset, Evaluator(LLM-as-judge 포함), Experiment 비교 기능이 있어 judge를 여기 얹는 방법도 있다
- **Inspect AI** (영국 AISI), **OpenAI Evals**: 범용 평가 프레임워크. dataset → solver → scorer 구조를 참고한다
